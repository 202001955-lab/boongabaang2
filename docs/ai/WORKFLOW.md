# 협업·Git 운영 규칙

## 1. 브랜치와 작업 단위

- 기준은 원본 저장소의 `main`이다. 상시 `develop` 브랜치는 만들지 않고, 작업별 짧은 브랜치를 PR로 합친다.
- 새 브랜치는 `feat/<task>`, `fix/<task>`, `test/<task>`, `docs/<task>`, `chore/<task>`를 사용한다.
  기존 `codex/...` 브랜치는 유효하다. 이름을 맞추려고 진행 중인 PR을 다시 만들지 않는다.
- 한 브랜치·워크트리에는 한 작업 주제를 둔다. 같은 PR에 합의된 후속 범위는 같은 브랜치에서 이어간다.
- 두 AI는 서로 다른 워크트리를 사용한다. 워크트리를 나눠도 같은 파일의 의미가 충돌할 수 있으므로
  작업 기록과 열린 PR에서 겹치는 변경을 먼저 확인한다. 겹치는 기능은 적용 순서나 담당 범위를 정한다.
- 다른 PR에 의존하면 기본적으로 그 PR 병합 후 최신 `main`에서 시작한다.
  급해서 쌓아 올리는 PR이 필요하면 base/head 의존 관계와 나중에 base를 바꿀 일을 기록한다.

## 2. 시작과 인수인계

다음 읽기 전용 점검으로 경로·브랜치·원격 저장소를 확인한다.

```sh
git status --short
git branch --show-current
git worktree list
git remote
git log -5 --oneline
```

원격 URL을 확인할 때 인증정보를 마스킹해서 확인하고, 토큰이 포함된 URL을 로그·대화에 그대로 출력하지 않는다.
`origin`이 원본인지 포크인지 이름만으로 판단하지 않는다. base 저장소와 push 저장소를 구분한다.
최신 base를 fetch한 다음 그 참조에서 새 브랜치·워크트리를 만든다. 이름과 경로가 이미 있으면 재사용 가능한 작업인지 확인한다.

기존 사용자 변경이 있는 경우 원래 작업 디렉터리를 그대로 보존한다.
이번 요청에 속하는 변경만 새 워크트리에 옮기고 파일 내용이 같은지 확인한다. 무관한 변경은 함께 커밋하지 않는다.
일괄 stash/pop이나 전체 파일 복사로 소유가 불분명한 변경을 섞지 않는다.

인수인계는 `docs/ai/tasks/<task>.md`를 기준으로 한다. 마지막으로 검증한 커밋 또는 파일 범위를 확인하고
현재 diff와 다르면 추가 검증 범위를 정한다. 기록만 믿고 이전 AI의 성공 상태를 재사용하지 않는다.
로컬 작업 기록은 다른 컴퓨터에 자동 공유되지 않으므로, 협업자가 이어받아야 할 기록은 승인된 브랜치에 커밋·푸시하고 PR에 연결한다.

## 3. 커밋

- 사용자 요청의 완료 지점에 맞춰 커밋한다. 구현·검증·PR까지 이미 맡겨진 작업에서 같은 승인을 반복해서 묻지 않는다.
  이 정책 파일 자체를 새로운 외부 작업의 승인으로 해석하지 않는다.
- 검토 가능한 한 가지 변경을 커밋한다. 메시지는 `fix: 빈 동네 이동 오류 방지`처럼 종류와 결과를 적는다.
  무관한 정리나 대형 포맷 변경을 끼워 넣지 않는다.
- 명시적인 파일 경로로 stage한다. `git add .`로 미확인 파일을 포함하지 않는다.
- 커밋 직전 `git diff --cached --name-only`, `git diff --cached`, `git diff --cached --check`를 확인한다.
  개인정보·키·환경 파일·보고서·개인 경로·불필요한 생성물이 있으면 제외하거나 작업을 중단하고 알린다.
- 계정의 공개용 Git identity/noreply 설정을 확인한다. 다른 사람을 author로 만들거나 개인 이메일을 임의로 노출하지 않는다.
  작업을 위해 전역 Git 설정을 바꾸지 않는다.
- 변경한 내용, 검사 결과, 알려진 한계를 작업 기록에 함께 남긴다. 아직 하지 않은 검사를 완료로 적지 않는다.

## 4. 푸시와 PR

1. 인증 계정, push 권한, base 저장소·브랜치, head 저장소·브랜치를 확인한다.
   연결 앱과 CLI가 다른 계정이면 섞어서 작업하지 않는다. 토큰 본문은 읽거나 출력하지 않는다.
2. 원본에 push 권한이 있으면 작업 브랜치를 푸시한다. 읽기 권한만 있으면 접근 가능한 포크의 작업 브랜치를 사용한다.
   특정 개인의 포크 이름을 공통 규칙에 고정하지 않는다.
3. 현재 작업 브랜치만 명시적으로 푸시한다. `main` 직접 push, `--all`, `--mirror`, 무심코 하는 force push는 사용하지 않는다.
4. 기존 PR이 있으면 갱신한다. 없으면 승인된 범위 안에서 원본 `main` 대상으로 만든다.
   구현 미완성·필수 검사 실패 상태를 공유해야 하면 draft로 표시하고 미해결 항목을 적는다.
   배포 권한 대기만으로 구현 실패로 분류하지 않는다. 미리보기 접근 제약은 별도로 기록한다.
5. [PR 양식](../../.github/pull_request_template.md)에 맞춰 비개발자가 확인할 결과와 개발 검증을 분리한다.
   최종 범위에 맞게 제목·설명을 다시 쓰고 작업 기록을 연결한다. 댓글을 새로 보내는 일은 사용자 요청 범위에 있을 때만 한다.
6. 원격의 PR head가 방금 푸시한 커밋인지, PR이 열려 있는지 확인한다.
   로컬 테스트 통과, 원격 CI 대기/실패, 배포 승인 대기를 구별해서 보고한다.

권한 오류가 나면 원인을 확인한다. 접근 가능한 정상적인 인증 수단·포크가 있으면 사용하되,
같은 실패를 반복하거나 권한·브랜치 보호를 약화하지 않는다. 해결에 사람이 필요하면 준비한 브랜치·PR과 정확한 차단 사유를 남긴다.

## 5. 동기화와 충돌

- 작업 시작 전에 base를 fetch한다. 오래 진행된 PR은 병합 전에 최신 base와 충돌·검증 영향을 확인한다.
- 기존 PR을 이어받으면 원격 head도 fetch해 로컬과 비교한다. 다른 AI가 추가한 커밋을 보존하고 동기화한 뒤 작업한다.
- 이미 공유한 브랜치는 base를 merge하는 방식을 기본으로 한다. 다른 AI가 사용하는 이력을 재작성하지 않는다.
- 아직 공유하지 않은 자기 브랜치는 필요하면 rebase할 수 있다.
  공유 브랜치의 rebase/force push가 명시적으로 요청되면 다른 작업자를 확인하고 백업 ref를 만든 뒤 `--force-with-lease`를 사용한다.
- 충돌은 두 변경의 의도를 확인해 해결한다. 파일 전체에 무조건 ours/theirs를 적용하지 않는다.
  판단할 근거가 없으면 충돌 부분과 선택지를 요청자에게 설명한다.
- `package-lock.json` 충돌은 `package.json`의 의존성 의도를 합친 뒤 해당 패키지 매니저로 다시 생성하고 diff·검증을 확인한다.
- 동기화·충돌 해결로 실행 코드가 바뀌면 관련 검사를 다시 한다. 문서만 바뀌면 문서 검증으로 범위를 제한한다.

## 6. 병합·배포·복구

- PR 생성 승인은 자동 병합·배포 승인이 아니다. 사용자가 맡긴 범위와 저장소 정책에 따라 진행한다.
- 병합을 맡았으면 최신 head의 검사와 요청자의 사용성 피드백을 확인한다. 자기 검토를 다른 사람의 승인으로 표시하지 않는다.
  관리자 우회나 CI 실패 무시는 하지 않는다. 저장소 설정이 허용하면 squash merge를 기본으로 하고 PR 단위 변경을 남긴다.
- 병합 뒤 원본 `main` 반영과 배포 상태를 별도로 확인한다. Vercel 권한 오류는 테스트 실패와 구분한다.
- 병합 전 수정은 후속 커밋을 기본으로 한다. 병합 후 되돌리기는 승인된 범위에서 revert PR로 수행하고 공유 이력을 reset하지 않는다.
- 정리 요청이 있으면 병합 여부와 미커밋 파일을 확인한 자기 작업 브랜치·워크트리만 제거한다.
  다른 AI가 사용하는 워크트리나 미푸시 작업은 보존한다.

## 7. 계속 갱신할 지식

- 새 오류·환경 제약: 해당 작업 기록에 근거와 해결/미해결 상태를 남긴다.
- 다른 작업에도 영향을 주는 구조·명령 변화: `PROJECT.md`를 갱신한다.
- 장기 운영 규칙 변화: `DECISIONS.md`에 이유와 대체 관계를 남긴다.
- 반복해서 필요한 절차: `.agents/skills/`의 기존 스킬에 반영하거나 별도 스킬을 만든다.
- 임시 실패 하나로 모든 작업에 새 승인·검사 단계를 강제하지 않는다. 적용 범위를 함께 적는다.
